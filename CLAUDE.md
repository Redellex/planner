## Commands

- `npm run dev` — start dev server (Cloudflare workerd runtime via Astro's Cloudflare adapter)
- `npm run build` — production build
- `npm run preview` — preview the production build
- `npm run lint` / `npm run lint:fix` — ESLint (type-checked rules)
- `npm run format` — Prettier (includes prettier-plugin-astro and prettier-plugin-tailwindcss)
- `npx astro check` — Astro/TypeScript type-check (not wired to a package.json script, but run in CI before build)
- `npm test` — Vitest, one run (`vitest run`). Tests live next to their module as `src/**/*.test.ts`. `vitest.config.ts` is plain (no Astro `getViteConfig`, which would load the Cloudflare plugin) and forces `process.env.TZ = "UTC"` so every OS runs like the Worker; `src/lib/test-runtime.test.ts` fails if it is not UTC. How to add a date test: `context/foundation/test-plan.md` §6.1.
- `npx stryker run` — manual mutation gate (Stryker, command runner over `npm test`) on `src/lib/availability.ts` per `stryker.config.json`; scope another module with `--mutate "src/lib/<file>.ts"`. Report in `reports/mutation/mutation.html` (gitignored). Not in CI or pre-commit.
- `npm run test:db` — database rules tests (pgTAP via `supabase test db`) in `supabase/tests/database/*.test.sql`: ownership of availability windows, month editability and locks, role changes including the last-manager guard, and the draft schedule rules (manager-only tables and RPC, a month lock that cannot be removed while a draft exists, atomic replace, shift shape/month/overlap constraints). Needs the local stack running (`npx supabase start`). Each file is one transaction that is rolled back, so it leaves no data. How to add one: `context/foundation/test-plan.md` §6.2.
- `npm run smoke` — dependency-free script (`scripts/smoke.mjs`) that walks the whole auth flow (sign-up → sign-in → protected page → sign-out) plus role enforcement (new user gets 403 on `/manager/users`; their POSTs to `/api/manager/months/lock` and to `/api/manager/users/role` promoting themselves get the 403 page with no effect — the month stays editable and they stay forbidden; an anonymous POST to a manager endpoint is sent to sign-in; the seeded manager gets 200, cannot demote the last manager, and stays manager) and the availability flow (the fresh user adds a window and gets an overlap error, then adds, edits and deletes a window in the last upcoming month; the manager locks a month, a create in it is refused, then unlocks) and the manager team view (the fresh user gets 403 on `/manager/availability` and leaves a 10:00–12:00 window on day 2 of station month + 3, which the manager then sees there) and the draft schedule flow (the fresh user's POST to `/api/manager/schedule/generate` gets the 403 page and an anonymous one is sent to sign-in, with no effect — the manager's `/manager/schedule` for station month + 3 still shows no draft and an open month; the manager then generates a draft there, sees it (`data-schedule-draft`), is refused the unlock with the discard-first message, discards and unlocks) over HTTP against a running server; `BASE_URL` env, defaults to `http://localhost:4321`; `SMOKE_MANAGER_EMAIL`/`SMOKE_MANAGER_PASSWORD` default to the seeded local manager, so it needs a database with `supabase/seed.sql` applied. The lock steps use the station month + 12, so it can be re-run without a DB reset; the edit/delete steps use station month + 3 (the last month `/availability` offers), which must not be locked locally. Each run leaves that run's fresh smoke user's windows on day 1 and day 2 of station month + 12 and on day 2 of station month + 3. If a run dies between the lock and unlock steps, that month stays locked and later runs fail at "availability create adds a window"; recover with `delete from public.availability_locks where month = '<YYYY-MM of station month + 12>-01';` in Studio. Generating locks station month + 3, so if a run dies between the generate and the final unlock, later runs fail at "availability create adds a window in an upcoming month"; recover as the manager by discarding that month's draft on `/manager/schedule` and unlocking it on `/manager/months`. Run after dependency upgrades. It complements `npm test` (pure-function unit tests) and `npm run test:db` (database rules) and does not replace them.
- `npm run check:ui` — dependency-free script (`scripts/check-ui-literals.mjs`) that fails on colour literals (palette classes, hex/rgb/hsl/oklch, `bg-cosmic`, gradient text, `backdrop-blur`) in the views already on design tokens; the scoped file list lives in the script. With file arguments it checks only those inside the scope.
- Pre-commit (husky + lint-staged, config in `lint-staged.config.mjs`, runs on the staged content only): `eslint --fix` then `vitest related --run` on `*.{ts,tsx,astro}` (only the tests whose imports reach a staged file), `node scripts/check-ui-literals.mjs` on `*.{astro,tsx}`, `prettier --write` on `*.{json,css,md}`; a staged migration or `scripts/smoke.mjs` runs `src/lib/station-time-zone.test.ts`, a staged `src/pages/**` file runs the route inventory guard `src/lib/route-inventory.test.ts`, and a staged `vitest.config.ts`/`package.json`/`package-lock.json` runs the whole suite. A failing lint or test blocks the commit.
- Claude Code agent hooks (`.claude/settings.json` → `.claude/hooks/*.mjs`, Node, no `jq`): after every `Write`/`Edit`, ESLint + the colour-literal check on that file only (no `--fix`) and the Vitest tests related to it (a station-time file runs the whole risk-#1 suite); on `Stop`, ESLint + colour literals on every changed file, the whole unit suite and `astro check`, sending the agent back at most once. Failures reach the agent as exit 2 + stderr.
- CI (`.github/workflows/ci.yml`) runs two jobs on push/PR to `master`: `ci` (`npm ci` → `astro sync` → lint → `astro check` → `npm test` → build, needs `SUPABASE_URL`/`SUPABASE_KEY` secrets) and `smoke` (spins up local Supabase via its CLI, pinned to 2.117.0 to match the devDependency, runs the database rules tests with `supabase test db` before anything mutates the data, then builds, serves the Cloudflare preview and runs the smoke script — no secrets needed).

## Architecture

Astro 7 SSR app (`output: "server"`, deployed via `@astrojs/cloudflare`) with React 19 islands, Tailwind 4, and Supabase for auth and role storage. All pages are server-rendered by default; API routes must export `const prerender = false` if they need to opt out of any default.

### Auth flow

- `src/lib/supabase.ts` — `createClient(headers, cookies)` builds a Supabase SSR client (`@supabase/ssr`) with cookie-based sessions, reading `SUPABASE_URL`/`SUPABASE_KEY` from `astro:env/server` (declared as optional server-only secrets in `astro.config.mjs`). Returns `null` when unconfigured — callers must handle that case (see the API routes below).
- `src/middleware.ts` — runs on every request, resolves the current user via `createClient(...).auth.getUser()`, attaches to `context.locals.user`, then reads the user's role from `public.profiles` into `context.locals.role` (`AppRole | null`; `null` when anonymous, unconfigured, or no row — fail closed, via `roleFromProfile`). The route lists and the decision live in `src/lib/route-access.ts` (`routeAccess` → `allow` / `signin` / `forbidden`); the middleware only maps the result. Redirects unauthenticated requests to `/auth/signin` for any path listed in `PROTECTED_ROUTES`. `MANAGER_ROUTES` (`/manager`, `/api/manager`, matched on segment boundaries) redirects anonymous users to `/auth/signin` and rewrites non-managers to `src/pages/403.astro` (status 403). `src/lib/route-inventory.test.ts` requires an expected access for every file under `src/pages`, so a new page or endpoint needs a row there (`context/foundation/test-plan.md` §6.3).
- API endpoints: `src/pages/api/auth/{signin,signup,signout}.ts` — read `FormData` directly (no schema-validation library is in use), call the corresponding Supabase auth method, and redirect with an `?error=` query param on failure. There is no JSON API convention to preserve here — auth endpoints are form-post + redirect.
- Auth pages: `src/pages/auth/{signin,signup,confirm-email}.astro`. Protected page example: `src/pages/dashboard.astro`.
- Roles: `public.profiles` (one row per auth user, created as `employee` by the `handle_new_user` signup trigger) holds `role` (`public.app_role` enum: `manager` | `employee`); TS side is `src/lib/roles.ts` (`AppRole`, `APP_ROLES`, `isAppRole`). Postgres is the real enforcement: RLS lets users read their own row, managers read all rows and update only the `role` column, and the `prevent_last_manager_demotion` trigger rejects demoting the last manager. Manager UI: `src/pages/manager/users.astro` + `POST src/pages/api/manager/users/role.ts` (form-post + redirect with `?updated=1&user=<id>` / `?error=…&user=<id>`; messages are allow-listed in `src/lib/manager-users.ts`).
- `src/lib/config-status.ts` exposes `missingConfigs` so pages can render a "Supabase not configured" banner instead of crashing when secrets are absent (see `src/components/Banner.astro`).

### Availability

- Tables (`supabase/migrations/20260926130000_create_availability.sql`): `availability_windows` holds one row per window (`employee_id` defaults to `auth.uid()`, `starts_at`/`ends_at`). A check keeps a window longer than 0 and at most 24h, and the `availability_windows_no_overlap` exclusion constraint (`btree_gist`) forbids overlapping windows per employee (half-open ranges, so back-to-back is fine). A window belongs to the month of its `starts_at`. `availability_locks(month)`: a row (first day of the month) means the month is locked. Managers insert/delete it via `/manager/months`; schedule generation inserts it too, and a month with a draft schedule cannot be unlocked (see Schedule).
- `public.is_availability_month_editable(month)` (SECURITY DEFINER) is true when the month is after the current station month and has no lock row. RLS uses it for every insert/update/delete of own windows, for both the month of `starts_at` and the month of `ends_at - 1µs` (so an overnight window cannot spill into a locked month; `20260926140000_harden_availability_writes.sql`), and update checks both the old and the new row; managers can read all windows. Only `starts_at`/`ends_at` are insertable and updatable (column grants).
- Timestamps are `timestamp without time zone` holding **Europe/Warsaw wall-clock** time. Handle them as strings/calendar parts (`"YYYY-MM-DDTHH:MM:00"`) and never pass them through `new Date(...)` (a UTC Worker shifts them). Durations (the 24h cap, and hour counts in scheduling) are wall-clock differences with no DST correction: on a DST day, 00:00–00:00 counts as 24h even though 23h or 25h actually pass. Station "now" lives in two places that must stay in sync: the `'Europe/Warsaw'` literal in the SQL helper and `STATION_TIME_ZONE` in `src/lib/availability.ts` (the smoke script's `stationMonthPlus` repeats it too). `src/lib/station-time-zone.test.ts` enforces this: every `at time zone '…'` in `supabase/migrations/*.sql` and every `timeZone: "…"` in `scripts/smoke.mjs` must equal `STATION_TIME_ZONE`.
- `src/lib/availability.ts` — pure helpers shared by pages and endpoints: station month and `upcomingMonths()`, `parseMonth`/`parseDate`/`parseTime`, `buildWindow` (end ≤ start rolls to the next day, so `00:00`–`00:00` is a full day), same-weekday expansion, Monday-first `calendarWeeks`, labels, the PostgREST error-code → message mapping and redirect URLs. Calendar math uses `Date.UTC` on date parts only.
- Routes: `/availability` (any signed-in user, `?month=YYYY-MM&day=YYYY-MM-DD`) is a Monday-first calendar grid for one of the next 3 months with a selected-day panel to add (optionally repeating on that weekday all month), edit and delete own windows; a locked month renders read-only. It filters `.eq("employee_id", user.id)` because managers can read everyone's windows. `/api/availability/{create,update,delete}` are form-POST + redirect endpoints that let RLS and the constraints decide. `/manager/months` and `/api/manager/months/lock` (manager-only via `MANAGER_ROUTES` in `src/lib/route-access.ts`) lock and unlock upcoming months idempotently. `/manager/availability` (manager-only via `MANAGER_ROUTES`, `?month=YYYY-MM&day=YYYY-MM-DD&employee=<profile id>`) is the read-only team view of the current station month plus the next 3: per-day counts of available people, a day panel of every account's windows, a lock-status line and a summary of each profile's window count and wall-clock hours (windows starting in the month only) with a "No availability submitted" flag. It reads with no `employee_id` filter, and every team list (profiles, month windows, carry-overs) goes through `loadAllPages` (count-driven paging) and `buildTeamView` in `src/lib/team-availability.ts`: if any list is not read in full the view is unknown and shows only the load error, month tabs and lock status, never empty states (§6.4). `?employee=` is honoured only when it equals a loaded profile id and narrows the calendar and day panel to that account. Its components live in `src/components/team-availability/`.

### Schedule

In plain terms (details in the bullets below):

- **Station day.** The station is open 24/7, so a "day" runs 06:00 → 06:00 the next morning. The night of Oct 31 → Nov 1 (00:00–06:00) belongs to October's schedule.
- **5 ways to split a day.** Each station day uses exactly one: 12+12, 8+8+8, 12+6+6, 6+6+12 or 6×4 hours. Someone is always on duty, never two people at once.
- **How shifts are resolved.** For each day the generator tries all 5 splits and keeps the best: the most hours covered first, then fair rotation (nobody gets more than one 12h shift or one night shift above the least-loaded person who could have taken it), then even total hours, then fewer shifts. A person only gets a shift that fits entirely inside their availability, at most one shift per day, and never two shifts back to back. A shift nobody can take is stored as **Uncovered**. Every unfairness the generator could not avoid is reported, never hidden.
- **Why unlock can be refused.** Generating locks the month, so employees cannot change availability under the draft. While a draft exists, unlock is refused ("Discard this month's draft schedule before unlocking it."). Discard the draft first, then unlock.

- Tables (`supabase/migrations/20261006120000_create_schedules.sql`): `schedules(month)` is one row (first day of the month) per month with a draft (`generated_at`, `generated_by` defaults to `auth.uid()`). Its `month` references `availability_locks(month)` `on delete restrict`: a draft needs its month lock, and **unlocking a month is refused (23503) while it has a draft**, so availability cannot change under a draft; `/api/manager/months/lock` turns that into `UNLOCK_WITH_DRAFT_ERROR` ("Discard this month's draft schedule before unlocking it.", `src/lib/schedule.ts`). `schedule_shifts` holds one row per shift: `month` references `schedules` `on delete cascade`, `starts_at`/`ends_at` are wall-clock like windows, and `employee_id` null means uncovered (`on delete set null`, so a deleted account's shifts become uncovered). Checks: `schedule_shifts_allowed_shape` (the 9 shapes below), `schedule_shifts_month_matches_station_day` (`month = date_trunc('month', starts_at - 6h)`), and the `schedule_shifts_no_overlap` exclusion, station-wide rather than per employee (one person on duty at a time; half-open, so touching shifts are fine).
- RLS: managers only (`is_manager()`) select, insert and delete on both tables; employees cannot read drafts at all. No update policy yet (S-04 adds what overrides need). Column grants: insert only `month` on `schedules`; `month, starts_at, ends_at, employee_id` on `schedule_shifts`. `public.replace_schedule_draft(target_month date, shifts jsonb)` (SECURITY INVOKER, so RLS and grants apply; execute for `authenticated` only) deletes the month's draft (shifts cascade) and inserts the new one in one transaction: one bad row (shape, month, overlap, missing lock) rolls the whole call back and the old draft stays. pgTAP: `supabase/tests/database/schedules.test.sql`.
- Station model (24/7): **station day D** = `[D 06:00, D+1 06:00)` for every calendar date D of the month, so a month's last station day ends at 06:00 on day 1 of the next month, and 00:00–06:00 on day 1 belongs to the previous month. Shapes (`SHIFT_SHAPES`, start/length): 06:00/12h, 18:00/12h, 06:00/8h, 14:00/8h, 22:00/8h, 06:00/6h, 12:00/6h, 18:00/6h, 00:00/6h. Every station day is exactly one of 5 patterns (`STATION_DAY_PATTERNS`): 12+12 (06–18 | 18–06), 8+8+8 (06–14 | 14–22 | 22–06), 12+6+6 (06–18 | 18–24 | 00–06), 6+6+12 (06–12 | 12–18 | 18–06), 6×4 (06–12 | 12–18 | 18–24 | 00–06). The night shift is the one covering 00:00–06:00 (18–06, 22–06 or 00–06), one per station day. Lengths are wall-clock, so 18–06 is 12h on a DST night too.
- `src/lib/schedule-generator.ts` — pure, deterministic `generateSchedule({ month, windows })` → `{ shifts }` sorted by `starts_at`. A person is eligible for a shift when their merged availability (`mergeAvailability`: windows starting in M plus carry-overs from M−1 ending after `M-01 06:00`, touching windows merged, so 18–24 + 00–06 covers 18–06) contains the whole shift; windows starting in M+1 are never read (that month is not locked). Hard rules: inside availability, at most one shift per person per station day, never two touching shifts (one ends when the other starts). Priorities: (1) cover as many minutes as possible; (2) the 12h rule: an assignee's 12h count ≤ the lowest 12h count among the shift's eligible members + 1; (3) the same night rule with night counts; (4) even total hours; (5) fewer shifts. Bounded for Workers Free CPU (median ~1.3 ms under Node for 40 people): a greedy pass per station day picks the best of the 5 patterns by (uncovered minutes, rule breaks, hours spread, shift count), filling the most constrained shift first; a repair pass capped at the number of shifts moves or same-day-swaps 12h/night shifts only when the sum of squared 12h and night counts strictly drops; one fill pass then assigns shifts the repair freed someone for. A shift stays uncovered only when every eligible person is blocked by a hard rule. Fairness is per month with no history, and there is no cross-month touching check: the last night of M and 06:00 on day 1 of M+1 can go to the same person.
- `src/lib/schedule-summary.ts` — `summarizeSchedule({ month, members, windows, shifts })` recounts from the shifts and the raw windows and never trusts the generator: `perMember` (`shifts`, `minutes`, `longCount`, `nightCount`, `hasAvailability`, `zeroShifts`), `uncovered`, `daysWithNoOne` (station dates with no assigned shift), `ruleBreaks` (`{ kind: "long" | "night", shift, assignee, eligibleMin }`) and `outsideAvailability` (always empty for a generated draft). It is the validation S-04 reuses to warn on overrides (FR-004); `daysWithNoOne` is what blocks accept/publish there.
- `src/lib/schedule.ts` — `?error=` messages and the `SCHEDULE_FEEDBACK_ERRORS` allow-list (`resolveScheduleFeedbackError`; `UNLOCK_WITH_DRAFT_ERROR` is shown on `/manager/months` only), `managerScheduleUrl` (status param first: `?generated=1&month=YYYY-MM`), `describeScheduleWriteError` (42501 → not permitted, 23503 → the month was unlocked), `scheduleMonths()` (current station month + next 3), `generatableMonths()` (next 3), `loadScheduleInputs` (profiles, month windows and carry-overs through `loadAllPages`; `buildScheduleInputs` → `ready | unknown`, §6.4) and `stationDayOf`/`shiftsByStationDay`.
- Routes (manager-only via `MANAGER_ROUTES`): `POST /api/manager/schedule/generate` (form `month` in `generatableMonths()`, optional `confirm=replace`) refuses an existing draft without the confirm, upserts the month lock, reads the team in full (unknown → `GENERATE_LOAD_ERROR`, nothing generated, the lock stays), generates and calls `replace_schedule_draft` (an unlock in between fails on the FK). `POST /api/manager/schedule/discard` (form `month` in `scheduleMonths()`) deletes the draft (0 rows → "No draft to discard") and keeps the lock. `/manager/schedule` (`?month=YYYY-MM&day=YYYY-MM-DD&confirm=replace`) shows a Generate form (upcoming months only) or the draft: Regenerate (a `?confirm=replace` panel posting `confirm=replace`), Discard, the days-with-no-one notice, a station-day calendar, a day panel with Uncovered markers, and the per-person summary with "No shifts", rule breaks and any outside-availability shifts. If any read is unknown it shows only the load error, month tabs and lock status. The draft panel carries `data-schedule-draft` (smoke marker). Components in `src/components/schedule/`, kitchen sink `src/pages/dev/schedule-states.astro`. Lifecycle: generate (locks) → regenerate/discard → unlock on `/manager/months` only once the draft is gone.

### Key conventions

- Path alias `@/*` → `./src/*` (`tsconfig.json`).
- Astro components for static content/layout; React components only where interactivity is needed (auth forms under `src/components/auth/`).
- Use the `cn()` helper from `@/lib/utils` (clsx + tailwind-merge) for conditional/merged Tailwind classes instead of concatenating strings.
- shadcn/ui components live in `src/components/ui/` (`components.json`: "new-york" style, neutral base color, lucide icons). Add new ones with `npx shadcn@latest add [name]`; the configured aliases are `@/components`, `@/components/ui`, `@/lib`, `@/hooks`.
- No Next.js directives (`"use client"`, etc.) — this is plain Astro + React islands.
- Supabase migrations go in `supabase/migrations/` as `YYYYMMDDHHmmss_short_description.sql`; enable RLS with granular per-operation, per-role policies on any new table. Use `public.is_manager()` (SECURITY DEFINER, avoids recursion through `profiles` RLS) in policies that need a manager check.
- After every migration, regenerate `src/db/database.types.ts` with `npx supabase gen types typescript --local` (local stack running); never hand-edit it. It is ignored by ESLint and Prettier. `src/lib/supabase.ts` types the client with it (`createServerClient<Database>`).

## 10xDevs AI Toolkit - Module 3, Lesson 3 (10xDevs 4.0 Hooks)

Treat a hook as a **quality gate the harness runs for the agent**, not a script you hope the agent notices. Hooks run outside the model, so they survive context compaction and forgotten instructions — but only a hook whose signal actually reaches the agent closes the loop:

```
test-plan.md "Quality Gates" -> pick the moment per gate -> /10x-configure-hook -> prove with sample JSON -> watch the agent fix a deliberate error
```

### Task Router - Where to start

| Skill                                                            | Use it when                                                                                                                                                                                                                                          |
| ---------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/10x-configure-hook`                                            | Turning the gates from `context/foundation/test-plan.md` into agent hooks, fixing hooks that fire but the agent never reacts to, or auditing an existing hook config. It detects the harness from the repo and carries dated per-harness references. |
| `/10x-test-plan --status`                                        | Read the current gates and rollout state. Changing which gates exist belongs to Lesson 1, not here.                                                                                                                                                  |
| `/10x-new` -> `/10x-research` -> `/10x-plan` -> `/10x-implement` | A hook surfaced a failure the agent cannot fix with a trivial correction (wrong business logic, flaky integration). Open a change instead of looping the hook.                                                                                       |

### Hook lifecycle

1. **Trigger** — an event in the harness: a tool finished editing a file, the agent is about to end its turn.
2. **Matcher** — narrows which tool calls or files the hook reacts to. Not every harness honours matchers the same way.
3. **Handler** — usually a shell command or script that reads the event payload as JSON on stdin.
4. **Signal** — what the hook returns. The exit code, stderr, stdout and JSON fields mean different things in different harnesses, and only one channel per event actually reaches the agent. **The signal channel differs per harness — check the skill's references before writing or reviewing a hook.**

A hook that runs but sends its message down the wrong channel is the most common failure: the user sees "hook error", the agent sees nothing and keeps going.

### Moments and layers

The slower the check, the rarer the moment:

| Moment                               | Typical checks                                                          | Reaches the agent?               |
| ------------------------------------ | ----------------------------------------------------------------------- | -------------------------------- |
| Per edit                             | Lint/format of **the edited file only**; related tests if they are fast | Yes, mid-work                    |
| End of turn (Stop or its equivalent) | Lint + tests for every file changed this turn, whole-project typecheck  | Yes, before the agent hands back |
| Pre-commit (git)                     | Lint + tests on staged files; catches edits made without the agent      | No — blocks the commit           |
| Pre-push (git)                       | Heavier suites, e2e that run locally                                    | No — blocks the push             |
| CI                                   | Integration, shared state, infrastructure you do not have locally       | No — PR feedback                 |

Local layers do not replace CI; each one saves a CI round-trip. Start with one per-edit lint hook and one end-of-turn typecheck, then add layers when you see what escapes.

### Contract

- Read the gates from the "Quality Gates" section of `context/foundation/test-plan.md` (by title, not section number). A gate the plan explicitly defers stays deferred unless the user overrides it — quote the deferral when you ask.
- Per-edit hooks check only the file that was edited. Never run `--fix` or a linter over the whole project on every edit.
- End-of-turn hooks that can send the agent back must stop after one retry (the harness's "already continued" flag or equivalent), so an unfixable error does not loop.
- Per-edit hooks only see the harness's edit tools; a file rewritten through a shell command skips them. The end-of-turn hook re-checks every file changed this turn (`git diff`), so it is the net for those edits.
- Timeouts are usually in **seconds**. Check the unit before copying a number.
- Prove every hook before trusting it: run the script with a sample payload on a deliberately broken file and on a clean one, then revert the error.
- Never overwrite existing hook config silently. Audit it, name the defects, merge, and show the diff.
