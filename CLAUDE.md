Today the owner is the only collaborator; adding one means moving the status to a GitHub App restricted to `master`. Ruleset "Protect master" (id 26309273) has rules `deletion`, `non_fast_forward` and the required status `ai-cr/verdict`, with the admin bypass in mode `pull_request` (the older `update` rule was dropped in Phase 5: it forced a bypass on every merge, which also skipped the verdict). Every `uses:` in `.github` is pinned to a full commit SHA with its tag in a comment, enforced by the repository setting `sha_pinning_required`; a new action needs a SHA pin or CI refuses to start.

## Architecture

Astro 7 SSR app (`output: "server"`, deployed via `@astrojs/cloudflare`) with React 19 islands, Tailwind 4, and Supabase for auth and role storage. All pages are server-rendered by default; API routes must export `const prerender = false` if they need to opt out of any default.

### Auth flow

- `src/lib/supabase.ts` — `createClient(headers, cookies)` builds a Supabase SSR client (`@supabase/ssr`) with cookie-based sessions, reading `SUPABASE_URL`/`SUPABASE_KEY` from `astro:env/server` (declared as optional server-only secrets in `astro.config.mjs`). Returns `null` when unconfigured — callers must handle that case (see the API routes below).
- `src/middleware.ts` — runs on every request, resolves the current user via `createClient(...).auth.getUser()`, attaches to `context.locals.user`, then reads the user's role from `public.profiles` into `context.locals.role` (`AppRole | null`; `null` when anonymous, unconfigured, or no row — fail closed, via `roleFromProfile`). The route lists and the decision live in `src/lib/route-access.ts` (`routeAccess` → `allow` / `signin` / `forbidden`); the middleware only maps the result. Redirects unauthenticated requests to `/auth/signin` for any path listed in `PROTECTED_ROUTES` (`"/"` there matches only `/` itself). `GUEST_ROUTES` (exactly `/auth/signin`, `/auth/signup`, `/auth/confirm-email`, not the `/auth` prefix) gives a signed-in user the `home` outcome, which the middleware maps to a redirect to `/`; `/api/auth/*` stays public for everyone. `MANAGER_ROUTES` (`/manager`, `/api/manager`, matched on segment boundaries) redirects anonymous users to `/auth/signin` and rewrites non-managers to `src/pages/403.astro` (status 403). `src/lib/route-inventory.test.ts` requires an expected access for every file under `src/pages`, so a new page or endpoint needs a row there (`context/foundation/test-plan.md` §6.3).
- API endpoints: `src/pages/api/auth/{signin,signup,signout}.ts` — read `FormData` directly (no schema-validation library is in use), call the corresponding Supabase auth method, and redirect with an `?error=` query param on failure. That param is never Supabase's text: `describeAuthError` (`src/lib/auth-feedback.ts`) maps `AuthError.code` (invalid credentials, unconfirmed email, existing account, weak password, rate limits) to an allow-listed message, anything else to the form's generic one, and `logAuthError` logs Supabase's raw code and message (never the submitted form fields). Sign-in redirects to `/`, sign-up to `/auth/confirm-email`, sign-out to `/auth/signin`. There is no JSON API convention to preserve here — auth endpoints are form-post + redirect.
- Auth pages: `src/pages/auth/{signin,signup,confirm-email}.astro`, each one `AuthPanel` (`src/components/auth/`); sign-in and sign-up render `?error=` only through `resolveAuthFeedbackError(form, param)`, whose allow-list is per form (a sign-up message in a sign-in link shows the sign-in generic text). The forms' `SubmitButton` takes `pending` from local state set after validation passes (native POST, no function action) and reset on a bfcache `pageshow`. Confirm-email is a guest route, so it renders only without a session and always shows one "Check your email" copy (`ConfirmEmailPanel.astro`). Kitchen sink `src/pages/dev/auth-states.astro`. Home: `/` is the signed-in dashboard (`src/pages/index.astro`, the protected page example); its link grid is `navLinksFor` without Home and Sign out lives in the top bar; the body is `src/components/dashboard/DashboardPanel.astro` (`data-dashboard`, a role pill from `roleLabel` in `src/lib/roles.ts`, kitchen sink `src/pages/dev/dashboard-states.astro`). The 403 page renders `src/components/system/AccessDeniedPanel.astro` ("Access denied", which smoke matches, and a "Go home" link; kitchen sink `src/pages/dev/access-denied-states.astro`). `src/pages/dashboard.astro` only answers 301 → `/` so old links keep working.
- Navigation: every page gets one top bar, `src/components/navigation/AppNav.astro`, mounted in `src/layouts/Layout.astro` from `locals.user`/`locals.role` (signed in = `user !== null`, as in the middleware) and `Astro.url.pathname`. Its links come from `src/lib/navigation.ts`: `NAV_LINKS` only names and orders pages, `navLinksFor(actor)` keeps those where `routeAccess` is `allow`, so the bar never offers a page the gate refuses and needs no list of its own (anonymous: Sign in, Sign up; signed in, with or without a role: Home, Availability, Schedule, Account; managers also Users, Months, Team availability, Manage schedule). Signed in, it also shows the email and Sign out; below `lg` everything collapses into a native `<details>` Menu (no hydration). Links carry `aria-current="page"` (`isCurrentNavLink`, exact match) and `data-nav-link=<href>` (smoke marker). `src/lib/navigation.test.ts` pins each actor's link set as literals and walks `src/pages` (`src/lib/page-routes.ts`, shared with the route inventory): a page outside `/api/` and `/dev/` needs a `NAV_LINKS` entry or a `NAV_EXCLUDED` row with its reason (`/dashboard`, `/auth/confirm-email`, `/403`). Kitchen sink `src/pages/dev/navigation-states.astro`. Pages have no "Back to dashboard" links; the bar's Home replaces them.
- Roles: `public.profiles` (one row per auth user, created as `employee` by the `handle_new_user` signup trigger) holds `role` (`public.app_role` enum: `manager` | `employee`); TS side is `src/lib/roles.ts` (`AppRole`, `APP_ROLES`, `isAppRole`). Postgres is the real enforcement: RLS lets users read their own row, managers read all rows and update only the `role` column, and the `prevent_last_manager_demotion` trigger rejects demoting the last manager. Manager UI: `src/pages/manager/users.astro` + `POST src/pages/api/manager/users/role.ts` (form-post + redirect with `?updated=1&user=<id>` / `?error=…&user=<id>`; messages are allow-listed in `src/lib/manager-users.ts`).
- Display name: `profiles.display_name` (null, or 1–40 characters with no surrounding Unicode whitespace and no control, zero-width or bidi-control character; `profiles_display_name_shape`, `20261007150000_display_name_visible_characters.sql`) is the name colleagues see on `/schedule`; null falls back to the email prefix. Only `public.set_display_name(new_name)` writes it (SECURITY DEFINER, caller's own row only, trims the whitespace `String.prototype.trim` strips (Postgres `btrim` alone strips only ASCII spaces), empty clears it, 22001 over 40 characters, 22023 for a forbidden character, execute for `authenticated` only); there is no column grant on it. The forbidden set lives in the migration and in `DISPLAY_NAME_FORBIDDEN` (`src/lib/account.ts`); keep them in step. **Never add an update policy for own rows on `profiles`**: `authenticated` holds `update (role)`, so such a policy would let a user promote themselves. UI: `/account` (any signed-in user via `PROTECTED_ROUTES`; `src/pages/account.astro` + `src/components/account/AccountPanel.astro`, kitchen sink `src/pages/dev/account-states.astro`) + `POST src/pages/api/account/display-name.ts` (form-post + redirect with `?updated=1` / `?error=…`); validation, messages and the allow-list live in `src/lib/account.ts`.
- `src/lib/config-status.ts` exposes `missingConfigs` so pages can render a "Supabase not configured" banner instead of crashing when secrets are absent (see `src/components/Banner.astro`, an English token `Alert` mounted by `Layout.astro`; its states are on `src/pages/dev/navigation-states.astro`).

### Availability

- Tables (`supabase/migrations/20260926130000_create_availability.sql`): `availability_windows` holds one row per window (`employee_id` defaults to `auth.uid()`, `starts_at`/`ends_at`). A check keeps a window longer than 0 and at most 24h, and the `availability_windows_no_overlap` exclusion constraint (`btree_gist`) forbids overlapping windows per employee (half-open ranges, so back-to-back is fine). A window belongs to the month of its `starts_at`. `availability_locks(month)`: a row (first day of the month) means the month is locked. Managers insert/delete it via `/manager/months`; schedule generation inserts it too, and a month with a draft schedule cannot be unlocked (see Schedule).
- `public.is_availability_month_editable(month)` (SECURITY DEFINER) is true when the month is after the current station month and has no lock row. RLS uses it for every insert/update/delete of own windows, for both the month of `starts_at` and the month of `ends_at - 1µs` (so an overnight window cannot spill into a locked month; `20260926140000_harden_availability_writes.sql`) and the month of the window's station day, `starts_at - 6h` (a window starting on day 1 before 06:00 belongs to the previous month's last station night, which that month's schedule reads, so it freezes with that month; `20261006130000_lock_last_station_night_windows.sql`), and update checks both the old and the new row; managers can read all windows. Only `starts_at`/`ends_at` are insertable and updatable (column grants).
- Timestamps are `timestamp without time zone` holding **Europe/Warsaw wall-clock** time. Handle them as strings/calendar parts (`"YYYY-MM-DDTHH:MM:00"`) and never pass them through `new Date(...)` (a UTC Worker shifts them). Durations (the 24h cap, and hour counts in scheduling) are wall-clock differences with no DST correction: on a DST day, 00:00–00:00 counts as 24h even though 23h or 25h actually pass. Station "now" lives in two places that must stay in sync: the `'Europe/Warsaw'` literal in the SQL helper and `STATION_TIME_ZONE` in `src/lib/availability.ts` (the smoke script's `stationMonthPlus` repeats it too). `src/lib/station-time-zone.test.ts` enforces this: every `at time zone '…'` in `supabase/migrations/*.sql` and every `timeZone: "…"` in `scripts/smoke.mjs` must equal `STATION_TIME_ZONE`.
- `src/lib/availability.ts` — pure helpers shared by pages and endpoints: station month and `upcomingMonths()`, `parseMonth`/`parseDate`/`parseTime`, `buildWindow` (end ≤ start rolls to the next day, so `00:00`–`00:00` is a full day), same-weekday expansion, Monday-first `calendarWeeks`, labels, the PostgREST error-code → message mapping and redirect URLs. Calendar math uses `Date.UTC` on date parts only.
- Routes: `/availability` (any signed-in user, `?month=YYYY-MM&day=YYYY-MM-DD`) is a Monday-first calendar grid for one of the next 3 months with a selected-day panel to add (optionally repeating on that weekday all month), edit and delete own windows; a locked month renders read-only, and on day 1 windows starting before 06:00 are read-only with a notice while the previous month is running or locked (`startsInPreviousStationNight`). It filters `.eq("employee_id", user.id)` because managers can read everyone's windows. `/api/availability/{create,update,delete}` are form-POST + redirect endpoints that let RLS and the constraints decide. `/manager/months` and `/api/manager/months/lock` (manager-only via `MANAGER_ROUTES` in `src/lib/route-access.ts`) lock and unlock upcoming months idempotently. The endpoint redirects through `monthsUrl` (`src/lib/manager-months.ts`): status param first (`?error=…` or `?updated=1`, which smoke matches as prefixes), then `&month=YYYY-MM`, and raw database errors are logged (`logMonthsError`) and replaced by `GENERIC_LOCK_WRITE_ERROR`. The page reads the locks through `buildMonthLocks` (ready | unknown): a failed read shows only `MONTHS_LOAD_ERROR`, never a month list or Lock/Unlock buttons. `?error=` goes through `resolveMonthsFeedbackError`, and the result is an `Alert` inside the row (`src/components/manager-months/MonthLockRow.astro`) of the `?month=` that `parseMonthParam` accepts (an upcoming month), otherwise at the top. Kitchen sink `src/pages/dev/manager-months-states.astro`. `/manager/availability` (manager-only via `MANAGER_ROUTES`, `?month=YYYY-MM&day=YYYY-MM-DD&employee=<profile id>`) is the read-only team view of the current station month plus the next 3: per-day counts of available people (from `lg` the calendar is the only part wider than `max-w-2xl`, like `/manager/schedule`, and each cell lists its windows as hours plus `calendarName`, up to 5 lines with "+N more"), a day panel of every account's windows, a lock-status line and a summary of each profile's window count and wall-clock hours (windows starting in the month only) with a "No availability submitted" flag. It reads with no `employee_id` filter, and every team list (profiles, month windows, carry-overs) goes through `loadAllPages` (count-driven paging) and `buildTeamView` in `src/lib/team-availability.ts`: if any list is not read in full the view is unknown and shows only the load error, month tabs and lock status, never empty states (§6.4). `?employee=` is honoured only when it equals a loaded profile id and narrows the calendar and day panel to that account. ### Schedule

In plain terms (details in the bullets below):

- **Station day.** The station is open 24/7, so a "day" runs 06:00 → 06:00 the next morning. The night of Oct 31 → Nov 1 (00:00–06:00) belongs to October's schedule.
- **5 ways to split a day.** Each station day uses exactly one: 12+12, 8+8+8, 12+6+6, 6+6+12 or 6×4 hours. Someone is always on duty, never two people at once.
- **How shifts are resolved.** For each day the generator tries all 5 splits and keeps the best: the most hours covered first, then fair rotation (nobody gets more than one 12h shift or one night shift above the least-loaded person who could have taken it), then even total hours, then fewer shifts. A person only gets a shift that fits entirely inside their availability, at most one shift per day, and never two shifts back to back. A shift nobody can take is stored as **Uncovered**. Every unfairness the generator could not avoid is reported, never hidden.
- **Review and publish.** The manager can change who works any draft shift (override), one station day at a time: the day's changes are saved together with one Save, all or none; changes that introduce a problem (together, e.g. one person on two shifts of the day) list it and need "Assign anyway" first, and a day that changed since the manager opened it is not saved. Publish is refused while any station day has no one assigned. A published month is frozen (no override, regenerate, discard or unlock) until the manager unpublishes it, which makes it a draft again. Every signed-in user, employee or manager, sees a published month on `/schedule`; drafts stay manager-only.
- **Why unlock can be refused.** Generating locks the month, so employees cannot change availability under the draft. While a draft exists, unlock is refused ("Discard this month's draft schedule before unlocking it."); while it is published, too ("Unpublish and discard this month's schedule before unlocking it."). Unpublish, discard the draft, then unlock.

- Tables (`supabase/migrations/20261006120000_create_schedules.sql`): `schedules(month)` is one row (first day of the month) per month with a draft (`generated_at`, `generated_by` defaults to `auth.uid()`). Its `month` references `availability_locks(month)` `on delete restrict`: a draft needs its month lock, and **unlocking a month is refused (23503) while it has a draft**, so availability cannot change under a draft; `/api/manager/months/lock` turns that into `UNLOCK_WITH_DRAFT_ERROR` ("Discard this month's draft schedule before unlocking it.", `src/lib/schedule.ts`). `schedule_shifts` holds one row per shift: `month` references `schedules` `on delete cascade`, `starts_at`/`ends_at` are wall-clock like windows, and `employee_id` null means uncovered (`on delete set null`, so a deleted account's shifts become uncovered). Checks: `schedule_shifts_allowed_shape` (the 9 shapes below), `schedule_shifts_month_matches_station_day` (`month = date_trunc('month', starts_at - 6h)`), and the `schedule_shifts_no_overlap` exclusion, station-wide rather than per employee (one person on duty at a time; half-open, so touching shifts are fine).
- RLS: managers only (`is_manager()`) select, insert and delete on both tables; employees cannot read drafts at all. Which months can get a draft (the next 3, `generatableMonths()`) is an app-level rule enforced only by the generate endpoint: the database lets a manager lock any month and write a draft for it (including past or current months) through PostgREST, so treat that window as a manager convention, not a guarantee. Column grants: insert only `month` on `schedules`; `month, starts_at, ends_at, employee_id` on `schedule_shifts`; table-level UPDATE is revoked on both (`20261006140000_revoke_schedule_updates.sql`), and the only update path is `update (employee_id)` on `schedule_shifts` with a manager-only update policy (the override: shape, times and month never change), used only through `save_schedule_day` (see Routes), so any new update policy must come with explicit column grants. `public.replace_schedule_draft(target_month date, shifts jsonb)` (SECURITY INVOKER, so RLS and grants apply; execute for `authenticated` only) deletes the month's draft (shifts cascade) and inserts the new one in one transaction: one bad row (shape, month, overlap, missing lock) rolls the whole call back and the old draft stays. `public.save_schedule_day(target_month date, station_day date, rows jsonb) returns integer` (`20261008120000_save_schedule_day.sql`; SECURITY INVOKER, so RLS, the column grant and the guard trigger apply to every row; execute for `authenticated` only) is the day save: `rows` = `[{ id, was, employee_id }]`, one per shift of the station day; 42501 for a non-manager, 22023 for a duplicate id, SP002 without a draft, SP001 when published, then it locks the day's stored shifts `FOR UPDATE`, returns 0 when the day is already stored as requested (every stored assignee equals its `employee_id`: the second request of an overlapping double submit, which waited on the first one's locks; `20261008130000_save_schedule_day_idempotent.sql`) and raises SP004 when their id set differs from `rows` or any stored assignee differs from its `was`; it updates only the rows whose `employee_id` differs from `was` (an updated count short of that → SP001 if a publish committed meanwhile, else SP004; an unknown assignee → 23503 on the FK) and returns how many it updated, all in one transaction. pgTAP: `supabase/tests/database/schedules.test.sql`, `schedule_day_save.test.sql`.
- Published state (`20261007120000_publish_and_override_schedules.sql`): `schedules.published_at`/`published_by` (null = draft) are written only by `public.publish_schedule(target_month)` and `public.unpublish_schedule(target_month)` (SECURITY DEFINER, check `is_manager()` themselves, execute for `authenticated` only), so `schedules` needs no UPDATE grant. Publish raises 42501 for a non-manager, SP002 without a draft and SP003 while a station day has no one assigned (covered days = `count(distinct (starts_at - 6h)::date)` over assigned shifts, the same rule as the app's `daysWithNoOne`, so an assigned 00:00–06:00 shift on M+1's day 1 covers M's last day), and is a no-op when already published (the first `published_at` stays). Unpublish: 42501, SP002 without a schedule, a no-op for a draft. **A published month is frozen by RLS plus one guard trigger**: shift insert/update/delete and the `schedules` delete (discard) apply only while `published_at is null`, so they affect zero rows or fail; the `schedule_shifts_published_guard` BEFORE trigger (`20261007130000_guard_published_schedule_shifts.sql`) locks the month's `schedules` row FOR SHARE before every direct shift write and raises SP001 when it is published, so a shift write racing `publish_schedule` (FOR UPDATE) either lands before publish counts coverage or is refused (RLS alone reads a snapshot and locks nothing). It applies to the table owner too (a manager's insert into a published month gets SP001, not 42501) but skips FK actions (`pg_trigger_depth() > 1`), so the cascade from a discarded or superuser-deleted `schedules` row and an account's set null keep working (deleting an assignee's account therefore turns their published shifts Uncovered, and the published card then shows "Since publishing, N days have no one … Unpublish to assign someone."); `replace_schedule_draft` raises SP001 before touching anything; the `schedules` row keeps the month lock (unlock → 23503). `describeScheduleWriteError` maps SP001 → `SCHEDULE_PUBLISHED_ERROR` ("Unpublish the schedule before changing it."), SP002 → `NO_SCHEDULE_ERROR`, SP003 → `PUBLISH_GAPS_ERROR`, SP004 → `DAY_CHANGED_ERROR` ("This day changed since you opened it. Reload and try again.").
- Station model (24/7): **station day D** = `[D 06:00, D+1 06:00)` for every calendar date D of the month, so a month's last station day ends at 06:00 on day 1 of the next month, and 00:00–06:00 on day 1 belongs to the previous month. Shapes (`SHIFT_SHAPES`, start/length): 06:00/12h, 18:00/12h, 06:00/8h, 14:00/8h, 22:00/8h, 06:00/6h, 12:00/6h, 18:00/6h, 00:00/6h. Every station day is exactly one of 5 patterns (`STATION_DAY_PATTERNS`): 12+12 (06–18 | 18–06), 8+8+8 (06–14 | 14–22 | 22–06), 12+6+6 (06–18 | 18–24 | 00–06), 6+6+12 (06–12 | 12–18 | 18–06), 6×4 (06–12 | 12–18 | 18–24 | 00–06). The night shift is the one covering 00:00–06:00 (18–06, 22–06 or 00–06), one per station day. Lengths are wall-clock, so 18–06 is 12h on a DST night too.
- `src/lib/schedule-generator.ts` — pure, deterministic `generateSchedule({ month, windows, previousNight? })` → `{ shifts }` sorted by `starts_at`. A person is eligible for a shift when their merged availability (`mergeAvailability`: windows starting in M, carry-overs from M−1 ending after `M-01 06:00` and M+1 windows starting on day 1 before 06:00 (the last station night; RLS freezes them with M), touching windows merged, so 18–24 + 00–06 covers 18–06) contains the whole shift; later M+1 windows are never read (that month is not locked). Hard rules: inside availability, at most one shift per person per station day, never two touching shifts (one ends when the other starts), including `previousNight`: the assignee of M−1's draft shift ending at `M-01 06:00` cannot start at 06:00 on day 1. Priorities: (1) cover as many minutes as possible; (2) the 12h rule: an assignee's 12h count ≤ the lowest 12h count among the shift's eligible members + 1; (3) the same night rule with night counts; (4) even total hours; (5) fewer shifts. Bounded for Workers Free CPU (40 people with a full-day window every day: median ~1.3 ms warm, ~9.5 ms on a cold first call under Node, so check real `cpuTime` with `wrangler tail` after deploy; `wallClockMinutes` parses by fixed position, and the greedy pass counts free candidates with an eligibility bitmap): a greedy pass per station day picks the best of the 5 patterns by (uncovered minutes, next-morning loss, rule breaks, sum of squared hours over members with availability, shift count), filling the most constrained shift first and, on a tie, the night first; a one-day lookahead keeps a night off the only person eligible for the next day's 06:00 start (their night would block it), both in the night's candidate order and as the next-morning-loss score (so after a day off for everyone the night run goes to whoever has fewer nights); "even hours" is the sum of squares, not max − min, because max − min misses a part-timer's gain while anyone else is still at 0; a repair pass capped at the number of shifts moves or same-day-swaps 12h/night shifts only when the sum of squared 12h and night counts strictly drops; one fill pass then assigns shifts the repair freed someone for. A shift stays uncovered only when every eligible person is blocked by a hard rule. Fairness is per month with no history. The cross-month touching check uses M−1's draft as it was when M was generated; if M−1 is regenerated later, `summarizeSchedule` reports the conflict.
- `src/lib/schedule-summary.ts` — `summarizeSchedule({ month, members, windows, shifts, previousNight?, nextMorning? })` recounts from the shifts and the raw windows and never trusts the generator: `perMember` (`shifts`, `minutes`, `longCount`, `nightCount`, `hasAvailability`, `zeroShifts`), `uncovered`, `daysWithNoOne` (station dates with no assigned shift; what blocks publish), `ruleBreaks` (`{ kind: "long" | "night", shift, assignee, eligibleMin }`) , `outsideAvailability` (always empty for a generated draft), `touchesPreviousNight` (shifts starting at `M-01 06:00` held by M−1's last-night assignee; empty unless M−1's draft changed after M was generated), and the per-person hard rules the database does not check (the overlap exclusion ignores `employee_id`): `sameDay` (pairs of one person's shifts in one station day), `backToBack` (one shift ending when the same person's next one starts, inside the month; a pair can be in both lists) and `touchesNextMorning` (shifts ending when `nextMorning`, M+1's draft shift starting at its day 1 06:00, begins, held by its assignee; the generator does not read M+1, so a regenerate of M after M+1 exists can cause it).
- `src/lib/schedule-override.ts` — pure `applyOverrides(shifts, changes)` (a map of shift id → new assignee, null = Uncovered) and `overrideWarnings({ before, after, shiftIds })`: the diff of two summaries (stored shifts vs. the same shifts with the day's changes applied) keeping only what the changes introduce together: `outside`, `sameDay`, `backToBack`, `previousNight`, `nextMorning` (each involving any changed shift, so a pair of two changed shifts is caught and listed once), `fairness` (a new 12h/night break, possibly on another shift) and `noOne` (a day left with no one). A warning is a problem for a person (its key includes the assignee), so a problem the old assignee already had on that shift is warned again for the new one, while a change that removes a problem warns nothing. An empty change set gives none (FR-004). The day save endpoint and `/manager/schedule` compute it the same way from their own full reads.
- `src/lib/schedule-day-save.ts` — the day form and its shared rules, pure: `parseDaySaveForm(form)` (rows from repeated `shift` fields with `was-<id>` and `employee-<id>`, `""` = Uncovered, plus the `confirmed` rows only with `confirm=override`; null when any row is missing or malformed), `changedRows` (`to ≠ was`), `matchesStored` (same shift set and every `was` stored), `alreadySaved` (same shift set and every `to` stored) and `sameRows` (equal as sets). A row is `DayRow` (`{ shift, was, to }`, `src/lib/schedule.ts`), encoded `<shift>:<was|none>:<to|none>` by `formatDayRow`/`parseDayRow`.
- `src/lib/schedule.ts` — `?error=` messages and the `SCHEDULE_FEEDBACK_ERRORS` allow-list (`resolveScheduleFeedbackError`; `UNLOCK_WITH_DRAFT_ERROR` and `UNLOCK_WITH_PUBLISHED_ERROR` are shown on `/manager/months` only), `managerScheduleUrl` (status param first — `error=`, `generated=1`, `discarded=1`, `overridden=1` ("Day saved."), `unchanged=1` ("No changes to save."), `published=1` or `unpublished=1` — then `month`, `day`, `confirm` (`replace` | `override`) and one `row=` per shift of the day (`formatDayRow`, each part URL-encoded on its own, literal `:`)), `parseShiftParam` (UUIDs only), `describeScheduleWriteError` (42501 → not permitted, 23503 → the month was unlocked, 23505 → confirm replacing, for a double submit, SP001–SP004 as above), `scheduleMonths()` (current station month + next 3), `generatableMonths()` (next 3), `loadScheduleInputs` (profiles, month windows, carry-overs, M+1 day-1 windows before 06:00, M−1's last night shift (`previousNight`) and M+1's first morning shift (`nextMorning`; the summary reads it, the generator does not), all through `loadAllPages`; `buildScheduleInputs` → `ready | unknown`, §6.4) and `stationDayOf`/`shiftsByStationDay`.
- Published view (`20261007140000_published_schedule_and_display_names.sql`): `public.get_published_schedule(target_month)` (SECURITY DEFINER, one `stable` SQL statement, execute for `authenticated` only) is the only path by which anyone but a manager reads shifts; no select policy on `schedules`, `schedule_shifts` or `profiles` was widened. It returns the month's shifts (`id, starts_at, ends_at, assignee_name, is_own, published_at`, ordered by `starts_at, id`; `20261007160000_published_schedule_is_own.sql`) only while `published_at` is set, and never another person's profile id, email, role or window: `is_own` (`employee_id = auth.uid()`) marks the caller's shifts. `assignee_name` is the display name, else `calendarName`'s rule (the email before `@` when `@` is past the first character, else the email, else the id's first 8 characters; the SQL and `src/lib/manager-users.ts` point at each other, keep them in step), and null when uncovered. A published month always has shifts, so an empty result means not published. `src/lib/published-schedule.ts` — `loadPublishedSchedule`/`buildPublishedSchedule` → `unknown | notPublished | published` (an error, no data or an assigned row without a name is unknown, never "Not published yet"; §6.4), `publishedScheduleUrl`, and its own `PublishedScheduleRow` (the generated types mark every column of a `returns table` function non-null). `/schedule` (any signed-in user via `PROTECTED_ROUTES`, `?month=YYYY-MM&day=YYYY-MM-DD`, months from `scheduleMonths()`, default the current station month) shows only the load error and the tabs, or "Not published yet" (managers also get a link to `/manager/schedule`), or the published card (`data-schedule-published`, publish time), the station-day calendar and a read-only day panel (`PublishedDayPanel`, names only, `data-shift-id`). `ScheduleCalendar` takes `labels` (key → name and optional `title`; `/manager/schedule` keys by profile id and passes `calendarName` + email, `/schedule` keys by `calendarAssigneeKey` from `src/lib/published-schedule.ts`: `own` for the viewer's shifts, `shift:<id>` for the rest, null when Uncovered), `hrefFor` and `ownEmployeeId` (`OWN_ASSIGNEE_KEY` on `/schedule`): the viewer's shifts get `bg-highlight/20` and "You", their days a `border-highlight` border unless the Uncovered/outside-availability colouring applies, and ", your shift" in the cell's `aria-label`. Each tab shows only its own station days (day 1 shows no previous-month night). Components in `src/components/published-schedule/`, kitchen sink `src/pages/dev/published-schedule-states.astro`. The published card on `/manager/schedule` links to it ("View published schedule"); the dashboard links "Schedule" for everyone and "Manage schedule" for managers.
- Routes (manager-only via `MANAGER_ROUTES`): `POST /api/manager/schedule/generate` (form `month` in `generatableMonths()`, optional `confirm=replace`) refuses an existing draft without the confirm, upserts the month lock, reads the team in full (unknown → `GENERATE_LOAD_ERROR`, nothing generated, the lock stays), generates and calls `replace_schedule_draft` (an unlock in between fails on the FK); a published month gets `SCHEDULE_PUBLISHED_ERROR` before the confirm check and the lock upsert. `POST /api/manager/schedule/discard` (form `month` in `scheduleMonths()`) deletes the draft and keeps the lock; 0 rows → `SCHEDULE_PUBLISHED_ERROR` when the row exists and is published, otherwise "No draft to discard". `POST /api/manager/schedule/override` is the day save (form `month` in `scheduleMonths()`, `day` a date of the month, the day form read by `parseDaySaveForm` (malformed or missing → `DAY_CHANGED_ERROR`), optional `confirm=override` with the `confirmed` rows; every redirect carries `month` and `day`). It reads everything in full (unknown → `GENERIC_SCHEDULE_WRITE_ERROR`, nothing written), then in order: no draft → `NO_SCHEDULE_ERROR`; published → `SCHEDULE_PUBLISHED_ERROR`; no changed row → `?unchanged=1`; the day already stored as requested (`alreadySaved`, the second click of a double submit) → `?overridden=1`; the posted shift set or any `was` not matching the stored day → `DAY_CHANGED_ERROR`; an unknown assignee → `INVALID_ASSIGNEE_ERROR`. It then recomputes `overrideWarnings` over all changed rows at save time (never taken from the panel); with warnings, unless `confirm=override` came with `confirmed` rows equal (as a set) to the posted rows, it redirects to `?confirm=override&row=…` (every row of the day in start order) without writing, so a pick changed during the confirm is checked again. Otherwise it calls `save_schedule_day` (23503 → `INVALID_ASSIGNEE_ERROR`, others through `describeScheduleWriteError`, SP004 → `DAY_CHANGED_ERROR`) and redirects `?overridden=1`. Two managers saving clean changes on different days at once can still create a same-day or back-to-back pair across the station-day boundary nobody was warned about, which the summary card shows on the next load: an accepted limit, since the database does not check per-person rules. `POST /api/manager/schedule/publish` (form `month` in `scheduleMonths()`) reads the draft row and the month's shifts in full (unknown → generic; coverage is `daysWithNoOne(month, shifts)` from `schedule-summary.ts`, which needs no team or windows), no draft → `NO_SCHEDULE_ERROR`, already published → `?published=1` (idempotent), `daysWithNoOne` non-empty → `PUBLISH_GAPS_ERROR`, then calls `publish_schedule` (which re-checks) → `?published=1`. `POST /api/manager/schedule/unpublish` calls `unpublish_schedule` → `?unpublished=1`. On an unlock 23503, `/api/manager/months/lock` reads `schedules.published_at`: set → `UNLOCK_WITH_PUBLISHED_ERROR`, otherwise `UNLOCK_WITH_DRAFT_ERROR`. `/manager/schedule` (`?month=YYYY-MM&day=YYYY-MM-DD&confirm=replace|override&row=…`) shows a Generate form (upcoming months only) or the draft card: on a draft, Publish (only while every station day has someone, otherwise "Assign someone on every day to publish (N days have no one).") next to Regenerate (a `?confirm=replace` panel posting `confirm=replace`) and Discard; on a published month, "Published — <month>", the publish time and only Unpublish. Then the days-with-no-one notice, a station-day calendar (from `lg` it is the only part wider than `max-w-2xl`, up to `max-w-6xl`, and each cell lists its shifts as hours plus `calendarName` (`src/lib/manager-users.ts`), the email before `@`, with Uncovered in red and an outside-availability line in yellow), a day panel with Uncovered markers (day 1 also shows M−1's last night read-only) that, on an unpublished draft, is one form: each shift's row (`data-shift-id`) has a "Who" select (`AssigneeSelect`, `employee-<id>`) with hidden `shift` and `was-<id>`, and one Save under the list posts the whole day; its result ("Day saved.", "No changes to save." or an error, placed in the day panel when the status comes with `day`) sits next to Save, and `?confirm=override&row=…` (rebuilt from the page's own reads: rows not matching the stored day → `DAY_CHANGED_ERROR`, no change, an unknown assignee or no warnings left → `OVERRIDE_NOT_SAVED_ERROR`) opens one confirm panel ("Save these changes?", one line per changed shift, one line per warning, except that every fairness warning folds into one "Check fairness: uneven 12h shifts for X; nights for Y" line linking to the summary's Fairness exceptions; "Assign anyway" / "Cancel") while the selects keep the pending picks, and the per-person summary with "No shifts", fairness exceptions, hard-rule exceptions (same-day and back-to-back pairs), any outside-availability shifts and any shift back to back with M−1's last night or M+1's first morning. If any read is unknown it shows only the load error, month tabs and lock status. The draft card carries `data-schedule-draft`, plus `data-schedule-published` once published (smoke markers). Components in `src/components/schedule/`, kitchen sink `src/pages/dev/schedule-states.astro`. Lifecycle: generate (locks) → override → publish → unpublish → regenerate/discard → unlock on `/manager/months` only once the draft is gone.

### Key conventions

- Local Supabase stack: `npx supabase start` (requires Docker); Studio at `http://localhost:54323`. Migrations in `supabase/migrations/` (`profiles`/roles, the availability tables and the schedule tables) and `supabase/seed.sql` are applied on start / `npx supabase db reset`.
- `supabase/seed.sql` is local/CI only (never run it against production): it creates a manager `manager@example.com` / `Manager-Passw0rd!` (id `00000000-0000-4000-8000-000000000001`) that the smoke script relies on, and an employee `employee@example.com` / `Employee-Passw0rd!` (id `00000000-0000-4000-8000-000000000002`), plus the demo team for e2e tests: `demo-full-a/b@` and `demo-part-c/d/e@example.com` / `Demo-Passw0rd!` (ids `00000000-0000-4000-8000-00000000000a`…`e`, the A–E of the mixed-team unit test) with windows in the station month + 1 at seed time, so generating that month lists only days 10 and 20 with no one. The month is fixed at reset: after a month boundary run `npx supabase db reset` or `npm run seed:demo`.
- Hosted project: migrations reach it via `npx supabase db push` (the project is linked).
- Production manager bootstrap: after that person signs up, run once in the Supabase SQL editor: `update public.profiles set role = 'manager' where email = '<email>';`
- Deploy: `npm run build` then `npx wrangler deploy`; set the two Supabase secrets via the Cloudflare dashboard or `npx wrangler secret put`.

## 10xDevs AI Toolkit - Module 5, Lesson 3 (Code Review in CI)

Move the review agent into GitHub Actions and turn its verdict into a merge gate. Evaluate prompt and model changes on a fixed case set before shipping them.

```
m5l3-requirements -> /10x-new -> /10x-research -> /10x-plan -> review.yml + composite action -> promptfoo evals
```

### Task Router - Where to start

| Skill / prompt / template                                                 | Use it when                                                                                                                                                                |
| ------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `m5l3-requirements` + `m5l3-cicd` (prompts)                               | Researching and planning the CI review workflow from written requirements.                                                                                                 |
| `m5l3-review.yml.template`, `m5l3-action.yml.template` (config templates) | Wiring the reviewer into a PR workflow: composite action with title, body and diff inputs, `ai-cr:passed` / `ai-cr:failed` labels and a failing check on a `fail` verdict. |
| `m5l3-promptfoo` (prompt) + `m5l3-promptfooconfig.yaml.template`          | Comparing models or prompt changes on the same diffs with is-json, llm-rubric and javascript assertions.                                                                   |
| `/10x-impl-review-ci`                                                     | Reviewing a PR against its `context/changes/<id>/plan.md` in CI with Claude Code Action; its workflow template lives in the skill's `references/`.                         |

### Hard rules

- **Pin third-party actions to a full commit SHA** with the tag in a comment.
- **Gate on the verdict field**, never on free-text output.
- **Pass multi-line values (diffs) through files or heredoc delimiters**, not single-line `$GITHUB_OUTPUT` writes.
- **Run the eval set before changing the review prompt or model.**
