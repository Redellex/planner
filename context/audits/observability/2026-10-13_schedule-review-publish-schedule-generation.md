# Observability audit: schedule review and publish, schedule generation (2026-10-13)

## 1. TL;DR

- **The middleware treats a failed auth or role read as "anonymous" or "no role"** (`src/middleware.ts:12-20`, `src/lib/route-access.ts:52-55`). During a Supabase problem, every manager action in both flows ends in a sign-in redirect or a 403 "Access denied". No log line is written and the invocation outcome is `ok`.
- **No log line can be traced back to who, what or when.** The `logScheduleError(context, error)` helper (`src/lib/schedule.ts:97-100`) and its six siblings take no user, month, day, caller or request id, and no deploy version. The shared loader `loadScheduleInputs` (`src/lib/schedule.ts:404-421`) logs "could not load team windows" with no month and without saying whether the page, generate or override called it.
- **Expected and unexpected outcomes share one channel.** Every refusal ends as a 302 with `?error=`, and the Location header is never recorded. Expected races (SP004, 23505, SP001) are logged with `console.error`. Several real anomalies write no line at all: an unparsable day form, a 0-row discard of an existing draft, an unknown assignee, and a confirm step the page cannot rebuild.
- **Database codes are reused for different causes.** SP004 means both "stale day" and "the update hit fewer rows than it should, so RLS or a grant regressed" (`supabase/migrations/20261008130000_save_schedule_day_idempotent.sql:86,108`). 23503 means both "month unlocked" and "account deleted". In each case a regression looks like a routine race.
- **Nothing records state changes or the stage reached.** Generate commits the month lock (`generate.ts:52`) before reading the team and running the generator. A CPU-limit kill, a throw or a load failure after that point leaves the month locked with no draft and no line saying so. A successful publish, unpublish, discard or day save is never logged, and unpublish and discard erase their own database evidence.
- **Most important consequence:** in the outage that matters most (Supabase degraded), managers are told "Access denied" or "This day changed, reload", and Workers Logs shows a run of ordinary 302, 403 and 200 responses. Nobody is alerted, and nothing in the logs says what broke.

## 4. Systemic root causes

1. **Fail-closed gates discard the error** (`src/middleware.ts:12-15`, `src/lib/route-access.ts:52-55`). Treating "can't tell" as "deny" is the right security decision, but the error object is dropped before anyone logs it. A Supabase or auth outage therefore turns into ordinary-looking 302 and 403 responses. _Explains P1 and the gate-related effects in both areas._
2. **The log helper has no context parameter, and each call site chooses its own payload** (`src/lib/schedule.ts:97-100`, `:404-421`, `:124`; `src/lib/published-schedule.ts:88-104`; `lock.ts:48,64`). The helper was written to keep raw DB text out of the UI, and it does that well. But it takes only a string and an error, so the knowledge of user, month, day, caller and stage never reaches the line. Some sites narrow the error to `{code, message}`, which drops `details`/`hint` (the transport cause) and the HTTP status. _Explains P2, R4, G2, G3, P8 and P9._
3. **The redirect convention gives every outcome the same shape and level** (all of `src/pages/api/manager/schedule/*.ts`; `describeScheduleWriteError` at `schedule.ts:102-126`). Every result is a 302, so status codes carry no signal. Expected races are logged as errors, and the `describe*` mapper logs a second time on its default branch. Validation and "nothing to do" branches log nothing. _Explains R1, R5, R6, R7, R8, R10, R12, P5 and P6._
4. **Database error codes are reused for different causes** (`20261008130000_save_schedule_day_idempotent.sql:86` and `:108` both raise SP004; 23503 at `schedule.ts:107` covers two foreign keys; publish's SP003 can arrive after the app's own pre-check passed). The app maps each code to one user message and one log text, so invariant violations look like races. _Explains R2, R8 and G6._
5. **Multi-step writes leave no record of the stage reached or of success** (`generate.ts:52-85`, `publish.ts`, `unpublish.ts`, `discard.ts`, `override.ts:131-150`). Generate commits the month lock first, then reads, generates and writes. Every later failure (a load error, a throw, a CPU kill) leaves that partial state behind, and nothing records it. Successful changes are not logged, and unpublish and discard null or delete the only database record. _Explains G1, G2, G4, G5 and R3._
6. **Astro's default error path catches throws before the runtime does, and there is no error page** (`astro/dist/core/routing/handler.js:101-108`; no `src/pages/500.astro`). Unhandled throws become empty 500s with a bare stack and an `ok` outcome. Throws after streaming starts are not logged at all (`render.js:66-72`). _Explains P3, P4 and G5._
